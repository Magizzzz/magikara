# MaGi Kara

macOS 原生日语卡拉 OK 字幕工作台。规格见 `MaGi_Kara_MVP_SPEC.md`。

目标流程只有五步：导入 MV/音频 → 粘贴日文歌词 → 点「AI 一键生成」→ 检查少量低置信度片段 → 导出 ASS。

---

## 环境说明（重要）

本机只有 **Command Line Tools，没有 Xcode**，所以：

- `xcodebuild` 不可用，`.app` 由 `Scripts/build.sh` **手工组装**；
- `XCTest` 不可用，测试用 CLT 里自带的 **swift-testing**（`Testing.framework`）；
- DSH 文件沙箱不允许写 `~/Library` 与 `/var/folders`，构建缓存全部被重定向到工程目录内；
- SwiftPM 自己的 `sandbox-exec` 在沙箱里无法嵌套，构建时加了 `--disable-sandbox`。

这些都已经封装进 `Scripts/build.sh`，正常情况直接用它即可。

## 关键实现决策

1. **读音用 macOS 自带能力，不引第三方**：`CFStringTokenizer`（日语分词）+ Latin 转写 +
   ICU `Latin-Hiragana`，全部离线。
   注意：**不能用 `String.applyingTransform(.toLatin)`**，它走中文拼音，实测「世界」会变成 `shì jiè`。

2. **真实对轨不是均分**：先在人声/静音与能量谷候选边界上做单调 DP 给每句定位，
   再在句内对音拍序列做带时长先验与浊音代价的强制对齐。
   Phase 0 报告里同时给出「均分基线」的误差用于对照。

3. **假名不单独存位置**：假名附轨完全由 `LyricLine.tokens` 的读音与音拍时间派生，
   主句移动时只需更新 `LyricLine`，不会出现两份状态失步。

4. **预览与导出共用同一套排版**：`KaraokeCanvas`（1920×1080）既是预览的排版坐标系，
   也是 ASS 的 `PlayRes`，所以「预览所见」与「导出所得」一致。

5. **ASS 的等待区/唱后停留区用独立静态事件**，不依赖空 `\k` 块在各播放器上的兼容性；
   扫色事件里汉字按字分享该词的音拍时长，`\k` 之和严格等于演唱时长。

6. **App 窗口**：手工组装的 bundle 若未注册到 LaunchServices，SwiftUI 的 `WindowGroup`
   会静默地不创建窗口。`build.sh` 打包后会调用 `lsregister`，
   `AppDelegate` 里另有兜底：启动后若没有可见窗口就自己建一个 `NSWindow`。

## 真实素材验证（2026-09-22 补充）

用一首真实的ニコカラ「On Vocal」文件（1920×1080 H.264 + AAC 48 kHz，174 秒）做了第一轮真实素材验证。
这一步暴露了 TTS 测试集**根本测不出来**的问题：

1. **人声检测在真实歌曲上完全失效**：该素材被压得很响，能量动态范围只有 **3.5 dB**，
   而旧实现用的是「噪声底 + 固定 6 dB」的绝对阈值 —— 阈值比整个动态范围还大，
   结果浊音比例 **0.0%**、人声段 **0 段**，`AI 一键生成` 会直接以
   「音频里没有检测到人声」**拒绝对轨**。
   修复后同一文件：浊音比例 **48.4%**、人声段 **96 段**，且第 1 段起点 7.02 秒与该文件
   实际 6.76 秒静音前导吻合（独立交叉验证）。

   **第一次修复引入了回归，值得记下来**：我一开始直接把判定依据整体换成
   「谱平坦度 + 人声频带能量占比 + 相对响度」的连续似然，结果压缩素材是修好了，
   但干净素材（TTS 基线）从 **199 ms 退化到 489 ms**，自动接受率从 92.5% 掉到 7.5%。
   原因是连续似然削弱了对齐代价的对比度，而动态范围健康时二值能量浊音本身就很准。
   最终方案是**按素材动态范围二选一**：
   - 动态范围 ≥ 8 dB → 走能量阈值 VAD（干净素材最准）；
   - 动态范围 < 8 dB → 走相对分位数的复合似然 VAD。
   修完两条路径同时达标：TTS 基线回到 199 ms，真实歌曲 VAD 正常。

2. **手写工程的媒体路径会解析失败**：`URL` 直接 Codable 时，裸路径
   `/a/b.mp4` 会解成没有 scheme 的相对 URL，AVFoundation 报 `unsupported URL`。
   已在解码时统一规范化成文件 URL，编码时写 `absoluteString`。

3. **缩略图生成会自锁**：原来用 `semaphore` 等一个内部 `Task` 去取 asset 时长，
   在协作线程池里会死锁，导致缩略图、波形、时长**全都拿不到**。已改为纯同步、时长由调用方传入。

4. **预览不画首帧**：`AVPlayerLayer` 在从未播放也从未 seek 过时不保证画出画面。
   现在加载媒体后会显式 `seek(to: 0)`。

5. **被限幅压平的素材画不出波形**：只画峰值会得到一整条实心色块。
   已改为「峰值外廓 + RMS 内部」的 DAW 常规画法。

以上都已通过真实文件实测：解码 173.96 秒 / 2,783,386 采样（与容器时长 174.03 秒一致）、
4005 个包络桶、14 张缩略图、预览正常出画。
另外确认该源文件**开头有 6.76 秒纯数字静音**（不是解码丢帧）。

**但真实歌曲的对轨精度仍然没有验证**，因为强制对齐需要用户提供歌词文本
（RD §8.2「歌词为真值」），这一步不能由我编造。

### 本轮为达标所做的修改

- **底部安全区**：`SubtitleStyle.bottomSafeAreaPositionY()`；默认值与三套预设全部落在安全区（原先默认 `positionY=-120` 在画面正中）；检查器加一键吸附按钮。
- **描边**：默认 3 → **7**，颜色改为近黑；假名原本用 4 向阴影假描边（宽度不随字号缩放），改为与主文字同一套 `AttributedString` 描边。
- **阴影**：`ASS BackColour` 存在**双重取反**（传了 `1-opacity`，而 `assColor` 内部已取反），导出阴影只剩 30% 可见、与预览不一致 —— 已修，并加了回归测试。
- **时间线**：`ScrollViewReader.scrollTo` 定位不准（要 00:27 却滚到 01:18），改为自行管理横向视口，附带拖动平移与播放跟随；新增 `--render-check` 生成渲染验收用的占位工程。
- **两个真实死锁**：`AudioDecoder.loadAudioTracks` 用信号量桥接 async API（在 `Task` 里调用会自锁）；以及并发首次创建 Core Text 字体导致整套测试挂死 —— 分别改为同步 API 与加锁字体缓存。

## 体验修复（时间线 / 导入 / 歌词输入 / Logo）

本轮的界面与交互修复，均为可用性修复，不动自动对轨主路径。

### 时间线点击定位

- **任意位置点击定位播放头**：时间尺、视频缩略图、波形、假名轨、歌词轨的**空白区域**
  都支持单击把 playhead 移到该位置，并同步预览与当前时间。
- 用 `SpatialTapGesture` 而不是 `DragGesture(minimumDistance: 0)`：
  前者拿到点击坐标且**不和「拖动平移」「拖动片段」抢手势**。
- **缩放不再错位**：点击手势挂在内容坐标系上（内容整体偏移 `-scrollX`），
  所以 `location.x` 就是内容坐标，与滚动、缩放无关；
  缩放时以「播放头在视口里的相对位置」为锚点（`TimelineGeometry.scrollXKeepingAnchor`），
  整条时间线不会乱跑。
- 边界处理：时间夹到 `[0, duration]`，**播放后仍能点回 0 秒**。
- 修复了一个既存 bug：歌词片段的边缘拖动判定区域用**视图内坐标**去和
  「绝对时间 × pps」比较，只有 `displayStart == 0` 的句子才碰巧正确。
- 回归测试：`TimelineGeometryTests`（8 项，含往返映射、边界、滚动、缩放锚点）。

  各自 ASR，按「歌词命中率 + 覆盖率 + 单调性 + 演唱区一致性 + 结构性离群」客观选优。
  **实测中置提取有害**（命中率 0.55 → 0.06，摇滚编曲下宽度信息被丢掉后模型更听不清）。
- **多次识别 + 平均分选择**：系统 ASR 逐次不确定（293/291/290 时间片），
  之前会翻出 32 秒级结构性错误；改为前 2 名各跑 3 次、按平均分选（接近时固定优先级），
  运行间波动从 0.8 秒压到 0.14 秒。
- **局部二次对齐**：只对无证据/低证据/结构性错位句，在局部窗口重切演唱区、
  用放大 1.6 倍的替换代价重跑逐字 DP；**拿不到证据就保持插值并把置信度压到 0.45**。
- **声学起点吸附**：实现并实测，**确认有害**（maxShift 越大越差），默认关闭。
- **两套指标**：`acousticOnset`（独立声学起点）与 `screenSubtitleTime`（画面字幕时间）并列报告，
  **不做全曲硬减偏移**，产品默认使用声学起点。
- **UI 信息架构**：顶部工具栏**移除**「AI 一键生成」；
  它固定在右侧「字幕」面板底部（「生成字幕时间」区块），与粘贴歌词→检查字幕形成顺序关系，
  不与「导出」等全局操作并列。

**仍未达标。** 并且诚实的 A/B 显示：本轮 B 配置（0.837/0.933/0.922）与第一轮 A 配置

## 自动对轨方案重构（第一轮）

完整报告：`TestAssets/ocr/ALIGNMENT_REBUILD.md`

旧的「能量 + 谱通量 + 音拍时长先验」在真实歌曲上句首平均误差 **5.095 秒**，
已重构为 **语音识别强制对齐**：

- **引擎**：macOS 26+ 系统自带 `SpeechAnalyzer` / `SpeechTranscriber`（`ja_JP`），
  完全离线、无第三方依赖；首次需下载模型，之后离线可用。
  171 秒真实歌曲识别 **2.0 秒**，完整对齐链路 2.4–3.7 秒。
- **算法**：按 ASR 时间空隙切「演唱区」→ 两层 DP（行区间 ↔ 演唱区 + 区内逐字 DP）→
  逐字时间 → ±0.3 秒音频局部修正。
  重复副歌靠顺序全局 DP 消歧，不依赖均分。
- **代价设计的关键**：不同字的替换代价必须高于留空，否则 DP 会把
  「オナってる」硬匹配到「笑ってちゃら」这类垃圾上，整块偏晚 4–14 秒。
- **能量/VAD 降级**为有声段检测与 ±0.3 秒局部修正，不再作为全曲主对齐器。
- **方法可见**：`AlignmentMethod` 区分 `asr-forced-align` / `ocr-screen-timed` /
  `legacy-energy-fallback` / `mock`；UI（侧栏 + AI 面板）、工程文件、ASS 头部
  都写明方法与证据分布。**OCR 画面时间永不冒充自动对轨**。

真实素材结果（35 行，对画面字幕时间）：

| 指标 | 旧方案 | 新 ASR 方案 | 产品目标 |
| --- | --- | --- | --- |
| 句首平均误差 | 5.095 s | **0.944 s** | ≤0.5 s ✗ |
| P90 | 8.910 s | **1.480 s** | ≤1.0 s ✗ |
| ±0.5 s 命中 | 1/35 (3%) | **11/35 (31%)** | ≥80% ✗ |

**提升 5.4 倍，但产品目标未达成**。误差里约 0.64 秒（中位）是系统性的
「字幕显示时间 vs 声学起点」差异 —— 已用能量/VAD 独立验证 ASR 侧的时间是准的
（第一段人声 0.74 s / ASR 0.78 s / 画面字幕 1.00 s）。去掉该分量后为
平均 0.713 s、±0.5 s 66%，但**这不计入达标结论**。

TTS 回归未退化：199 ms / 62% / 92.5%；全量 **80 tests 全部通过**。

## 真实素材可行性验收（上一轮结论）

完整报告：`TestAssets/ocr/FEASIBILITY.md`

用一首真实日文歌曲 MV（画面自带中日双语硬字幕，171 秒）做了端到端实验，
歌词由 macOS Vision 从画面 OCR 得到（35 行，覆盖 1–151 秒，平均一致度 0.84），
再用**画面字幕的出现时间作为独立真值**评估音频自动对轨。

**结论：音频自动对轨在真实歌曲上不可用。**

| 指标 | 数值 |
| --- | --- |
| 句首误差（绝对值） | 平均 **5.095 秒**（中位 4.330，P90 8.910，最大 14.070） |
| 落在 ±0.25 / ±0.50 / ±1.00 秒内 | **1 / 1 / 3**，共 35 行 |
| 误差 vs 时间的线性拟合 | R² = 0.09（不是整体偏移或简单漂移，线性校正无效） |

原因：该素材动态范围只有 **3.3 dB**（限幅压平），能量几乎不携带「哪里在唱」的信息；
起音点 8.9 个/秒被鼓点主导。代价函数里只剩「音拍时长先验」有区分度，
DP 实际退化成按先验铺开 —— 对轨给出的演唱总时长 63.0 秒 vs 画面字幕实际 94.0 秒。

试过并实测的两个改进（**都已回退**，不把未证实有效的改动留在代码里）：

| 实验 | 改动 | 真实素材误差 |
| --- | --- | --- |
| A | 收紧区间时长带 + 时长权重 3.0→6.0 | 4.427 秒（仍不可用） |
| B | 似然特征换成「人声频带绝对能量」 | **10.430 秒**（更差） |

按 RD §13 的 Phase 0 验收门槛（「至少在一段常规 J-Pop 上生成明显可用的自动 Timing」），
**未通过**；按规格要求应先改对齐方案，再进入后续大规模 UI 开发。

另一方面，**字幕成品本身在真实素材上是达标的**：把时间换成 OCR 得到的真实字幕时间后，
6 条效果验收标准在真实视频上全部通过（截图 `ui-real-sweep.png` / `ui-real-replace.png`），
工程与 ASS 导出为 `real-nanmonee-ocr-timed.{magikara,ass}`。
注意该工程的行内音拍时间是**平均分配占位**，工程里已逐句标注。
